# marsdawn.southern-light.dev

The website of [MarsDawn](https://marsdawn.southern-light.dev), a Markdown editor for the Mac, in four languages: English, Traditional Chinese, Simplified Chinese and Japanese. English and Traditional Chinese are the app's own interface languages; Simplified Chinese and Japanese extend the site's reach beyond that — see PRODUCT.md's Site constraints.

## Layout

| Path | What it is |
|---|---|
| `public/` | The site root, served as static files |
| `public/_redirects` | The site's redirects, generated by `build_pages.py` from its `redirects()`. Cloudflare reads the file and never serves it. `/go/app-store` is the one link to publish for the Mac App Store listing: it goes to the home page before launch and to the listing from launch day, so a posted link never has to change |
| `public/_headers` | Security headers for every page (CSP, nosniff, no referrer) and cache rules (theme index short, versioned theme files long). Scripts are limited to the site's own (`script-src 'self'`), Google Tag Manager, and the two small inline scripts in every page's `<head>` (Consent Mode default, then the GTM loader), each allowed by its own sha256 hash — see the comment above the CSP line. Anything that adds a script, inline style, web font or third-party resource must update the CSP |
| `scripts/build_pages.py` | Generates every page into `public/`, with the en and zh-Hant copy. Also generates the consent-mode head scripts and banner markup on every page (`consent_head_html`, `consent_banner_html`) for the site's GA4-via-GTM analytics (owner decision, #71): every storage type defaults to denied until the visitor accepts in the banner, whose choice lives only in `localStorage`, never a cookie of ours. `public/assets/consent.js` (hand-written, not generated) is the banner's behaviour. The site deliberately never embeds GTM's `<noscript>` iframe, because it would load before any consent choice exists |
| `scripts/copy_zh_hans.py`, `scripts/copy_ja.py` | The zh-Hans and ja copy, merged in by `build_pages.py`, covering the same pages as en/zh-Hant. A locale may still have only some pages if one hasn't been translated yet; nothing links to a page that locale doesn't have |
| `scripts/check_hreflang.py` | Checks that every page's hreflang set is complete (every locale that has the page) and reciprocal, in the HTML and the sitemap (runs in CI) |
| `scripts/check_links.py` | Checks that every same-site link in the built site points at a file that exists (or a source in `public/_redirects`), and that any Mac App Store listing link is the country-less `…/app/id<digits>` form (runs in CI) |
| `scripts/check_redirects.py` | Checks `public/_redirects`: every destination is a page of this site or the Mac App Store listing, carries no tracking parameters, and `/go/app-store` goes where the launch phase allows (the home page before launch, the listing after). `--self-test` plants a break of each kind first (runs in CI) |
| `scripts/check_offers.py` | Checks that every schema.org Offer in the built site states an availability, and that it's PreOrder or InStock (runs in CI) |
| `scripts/check_invariants.py` | Checks the whole-site invariants for the launch phase the build is in, read from `AVAILABILITY`: four-locale page parity, the footer's Mac App Store line, coming-soon wording and listing links (runs in CI) |
| `content/legal/` | The single-source Markdown for the legal pages (currently just `privacy.<locale>.md`; issue #33), and its cache: `<slug>.<locale>.rendered.html` plus `manifest.json` (a sha256 of every source and rendered file, and the kit tag). `build_pages.py` reads the cache, not the Markdown, so the site still builds on Ubuntu CI with no Swift toolchain |
| `scripts/render_legal.py` | Renders `content/legal/*.md` through the kit's own `MarkdownRenderer` (the app's preview renderer) and vendors `public/assets/preview.css` and `public/assets/themes.css` from the same pinned kit tag as `tools/hero-render`. Needs macOS; rerun it after editing a legal page's Markdown or bumping the kit tag, then commit its output |
| `scripts/check_legal_render.py` | Checks that `content/legal/`'s cached HTML and the vendored CSS still match `manifest.json`'s recorded hashes, and that the manifest's kit tag matches `tools/hero-render/Package.swift`'s pin — a Swift-free consistency check, not a re-render. `--self-test` plants a break of each kind first (runs in CI) |
| `scripts/check_theme_index.py` | Checks the published gallery tree `public/themes/v1/` (index, versioned files, previews, `published.json`) against `themes/`, and, in CI, against the base branch and the PR author's class (bot / maintainer / anyone else). Mandatory. `--self-test` plants a break of each rule first (runs in CI). **Advisory for any PR that touches `scripts/**` or `.github/**`**: the check runs the PR's own copy of itself and of the workflow, so such a PR can weaken it; the diff review is the gate there, and a non-maintainer or bot PR touching those paths fails by rule (a rule the PR could also edit — which then shows in the diff) |
| `scripts/build_themes.py` | Publishes `themes/<id>/theme.json` to `public/themes/v1/<id>/<version>/` (theme.json and light/dark previews rendered by the pinned kit CLI), never re-rendering a published version, and writes `index.json`, the append-only `published.json`, and the pages. Needs macOS + Swift (it builds the CLI the way `sync_theme_kit.py` does). Commit `themes/` first, then run it and commit its output |
| `themes/` | The gallery's build input: one `<id>/theme.json` per listed theme, and `revoked.json` (`[]` when nothing is revoked). Delist by removing the folder; revoke by also adding the id to `revoked.json` |
| `vendor/kit-themes/<sha12>/` | The kit's theme contract, vendored at a pinned **commit** (`ThemeStyles.json`, the four built-in `theme.json`, the validator's own fixtures, `preview.css` and its `.sim-preview`-scoped twin `preview-sim.css`, and `expected-css/` — byte-exact `theme css --json` output for every valid fixture, every built-in, and a generated sweep of every style option). This is what the theme simulator's (`/themes/new/`) JavaScript ports are checked against, since a port can drift from what it copies |
| `scripts/sync_theme_kit.py` | Builds `marsdawn` from a detached git worktree of the pinned kit commit (needs macOS + Swift + a local clone of `mars-dawn-kit`) and writes `vendor/kit-themes/<sha12>/`. Rerun it after bumping `KIT_SHA` in the script, then commit its output |
| `scripts/rescope_css.py` | The `.sim-preview` rescoping transform's Python half (the sync-time twin of `public/assets/theme-sim/rescope.js`'s runtime half): turns `preview.css` into `preview-sim.css`. Shares `scripts/theme_sim/rescope_fixture.json` with the JS module's own test, so neither can drift from the other |
| `scripts/check_theme_kit.py` | Checks that `vendor/kit-themes/<sha12>/` still byte-matches GitHub's raw copy of the pinned kit commit, that every file matches its own `manifest.json` hash, that the sweep covers every `ThemeStyles.json` option and every scalar style option, and that `rescope_css.py` still passes its fixture — a Swift-free consistency check, not a re-sync (runs in CI). `--self-test` plants a break of each kind first |
| `scripts/submission/` | The theme submission workflows' logic (`gate.py`, `kit_cli.py`, `validate.py`, `comment.py`, `stage.py`, `publish.py`) and its unit tests on synthetic event payloads (`run_tests.py`, in CI). The workflows only call these; see "Theme submissions" below |
| `scripts/check_workflows.py` | Static rules for every workflow: no `${{ github.event.* }}` inside `run:`, no `pull_request_target`, every `uses:` pinned to a full commit SHA, no write permission in a job that runs brew/swift/the kit. Reads the YAML with its own fail-closed subset reader (no PyYAML in CI). `--self-test` plants a break of each rule first (runs in CI) |
| `.github/ISSUE_TEMPLATE/theme-submission.yml` | The issue form the simulator's **Submit** fills in (`template=theme-submission.yml`, field `theme`), with the DCO checkbox |
| `scripts/deploy.sh` | Manual deploy, for emergencies |
| `wrangler.jsonc` | Cloudflare Workers static-assets config |

These URLs are public contracts and must keep working at the same paths:
`/privacy/`, `/support/`, `/zh-hant/privacy/`, `/zh-hant/support/`, `/zh-hans/privacy/`, `/zh-hans/support/`, `/ja/privacy/`, `/ja/support/` (linked from the App Store).
`/go/app-store` is one too, once anything outside the site links to it: it is a redirect, not a page, and only its destination may change.

`/themes/v1/` is a public contract for the theme gallery, whose design is `docs/theme-ecosystem-design.md` in the app repository. `public/themes/v1/index.json` is built from `themes/` by `scripts/build_themes.py`; files under `public/themes/v1/<id>/<version>/` never change once published, and `public/themes/v1/published.json` records every one of them. `scripts/check_theme_index.py` is mandatory on every push and pull request. The cache rules in `public/_headers` give the index the short lifetime §5.1 describes and the versioned files a long, immutable one.

Theme PRs are judged by who opens them (by GitHub user id): the `github-actions[bot]` submission flow may add one theme and its generated files; a maintainer (repo variable `THEME_MAINTAINER_IDS`, default the owner's id) may do anything the rules allow, including delisting and revoking; anyone else may not touch `public/themes/v1/`, `themes/revoked.json`, `scripts/` or `.github/`. The labels `theme-author-change` and `theme-version-rollback` relax one rule each; anyone with triage access can apply a label, so the rollback label only counts on a maintainer's PR. **`check` is advisory for any PR that touches `scripts/**` or `.github/**`** — it runs that PR's own copy of the check — so review those diffs yourself; a green `check` doesn't vouch for them.

## Theme submissions

Design §3.2 in the app repository; plan-website-104 W2 (#143). No secrets are involved, nothing runs on a self-hosted runner, and each job that touches submitted text with the kit or a toolchain holds no write scope.

1. **Submit.** The simulator's **Submit** opens the `theme-submission` issue form with the theme's JSON filled in; the designer ticks the DCO box. `theme-submission.yml` (issue opened/edited, one run per issue at a time) reads the body through the API (`gate`, no permissions), validates the exact bytes with the kit CLI at the pinned commit on macOS (`validate`, no permissions), and writes one comment by `github-actions[bot]` (`comment`, `issues: write` only) with the verdict, the kit's messages in a fence, and the validated sha256.
2. **Approve.** A maintainer adds `theme-approved`. `theme-approve.yml` acts only when the sender's numeric id is in `THEME_MAINTAINER_IDS`, the theme's sha256 equals the latest validation comment's (verdict valid), the DCO box is still ticked, and `author.github` is the issue opener's login (unless the issue has `theme-author-change`). `theme-pr.yml` then commits the theme, runs `build_themes.py` on macOS (no permissions) and, in a separate job with the only write scopes, re-checks every path, size and PNG, commits as `github-actions[bot]` with the submitter as co-author, pushes `theme/issue-<n>` and opens a PR into `THEME_BASE_BRANCH` (repo variable; default `main`).
3. **Run CI on the bot PR.** A PR opened by the workflow token starts no workflows: close and reopen it to run `check`. Review the theme file, both previews and the index entry, then merge when `check` is green.

Git users open a PR that adds or changes only `themes/<id>/theme.json`, every commit signed off (`git commit -s`), with `author.github` set to their own login. That PR is data: a maintainer runs **Actions → Theme from pull request** with its number. The workflow reads that one blob through the API (never the PR's code), checks the author and every `Signed-off-by`, builds and opens a new bot PR with the designer as co-author, and closes the original with credit.

Issue-triggered workflows only run from the default branch, so this flow first runs for real once it reaches `main`.

## Editing

Edit the copy in `scripts/build_pages.py`, then regenerate and commit the output:

```sh
python3 scripts/build_pages.py
```

UI labels quoted on the pages must match the app's strings in each language. Check them by hand when either side changes.

Preview locally:

```sh
python3 -m http.server 8765 --directory public   # http://localhost:8765/
```

After a deploy, open every page in a private window. They must load without a login or redirect.

## Branches and deploys

- `main` holds the latest work. Pull requests target `main`.
- `release` is what the site serves. A push to `release` deploys through GitHub Actions (`production` environment). To publish, fast-forward `release` to `main`:

  ```sh
  git push origin main:release
  ```

- Every push and pull request runs the check: the regenerated pages must match the commit, and `public/themes/v1/` must be valid against `themes/` and the base branch. A newer push to a PR cancels that PR's older check run.

The deploy needs two settings on the `production` environment:

| Kind | Name |
|---|---|
| Secret | `CLOUDFLARE_API_TOKEN` (Workers Scripts: Edit only) |
| Variable | `CLOUDFLARE_ACCOUNT_ID` |
